# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AgentFloor is a web UI wrapping the [TradingAgents](https://github.com/TauricResearch/TradingAgents) Python multi-agent LLM framework. It is **research-only** — no order execution, with one fenced exception: the opt-in JEV Lab module can place Alpaca *paper* orders (never live; see JEV Lab below). The stack is FastAPI + async SQLAlchemy 2 + PostgreSQL (backend) and Next.js 16 App Router + NextAuth v4 + TanStack Query v5 + Tailwind CSS v4 (frontend).

```bash
# Install (uv manages the virtualenv automatically)

# Run dev server
python -m uvicorn main:app --reload

# Run all tests (requires running Postgres; see docker-compose.dev.yml for the db service)
python -m pytest

python -m pytest tests/test_auth.py::test_register_first_user_is_admin

# Database migrations
DATABASE_URL=postgresql://agentfloor:agentfloor@localhost:5433/agentfloor alembic upgrade head
DATABASE_URL=postgresql://agentfloor:agentfloor@localhost:5433/agentfloor alembic revision --autogenerate -m "description"
```

### Frontend

```bash
cd frontend

npm install
npm run dev      # http://localhost:3000
npm run build    # production build (outputs standalone via next.config.mjs output: "standalone")
npm run lint
npx tsc --noEmit # type-check without emitting
```

### Full stack (Docker)

```bash
# Copy and fill in secrets first
cp .env.example .env

docker compose -f docker-compose.dev.yml up --build        # starts db, backend, frontend, nginx
docker compose -f docker-compose.dev.yml up db             # just postgres (for local backend dev)
```

Local Postgres from `docker compose -f docker-compose.dev.yml up db` is mapped to **port 5433** (not 5432) to avoid conflicts.

**Markov regime analysis:** `services/markov_service.py` fits a 3-state (Bull/Sideways/Bear) Gaussian HMM on 2 years of daily returns via `hmmlearn` (optional dependency — install with `pip install -e ".[markov-hmm]"`). Returns current regime, directional signal (`bull_prob − bear_prob`, range −1 to +1), walk-forward Sharpe, max drawdown, and the 3×3 transition probability matrix. Results are cached in-process for 1 hour. The endpoint is authenticated (`Depends(get_current_user)`).

**JEV Lab (`backend/jev_loop/` + `services/jev_*.py`):** The one exception to "no order execution", fenced hard. A market-making loop (spec: `docs/superpowers/specs/2026-09-26-jev-lab-design.md`). `jev_loop/` is a pure package (no I/O): state snapshot, the seven-question Jev battery + arithmetic guard (`split.py`), policy, strategy thresholds, Avellaneda-Stoikov pricing, nine hard risk limits, fallback ladder, order planner, calibration. `services/jev_loop_runner.py` runs the tick loop; `jev_session_manager.py` owns tasks (max 2 running, 1 paper session per symbol), the DB sink + WebSocket broadcast, startup recovery (running → `interrupted`, paper orders cancelled; never blocks boot) and nightly tick retention (14 days). `jev_client.py` resolves the decider: valid `typesafe` key → valid `ai_gateway` key (Vercel AI Gateway, `typesafe-ai/jev`) → labelled mock. Jev's upstream hosts (TypeSafe, DigitalOcean) rate-limit per model with no rate-limit headers, so each Jev call is a single request (a 429 is never retried inside a tick) and `jev_loop/pacing.py` spaces calls (`jev_interval_s`, default 6 s; doubled on 429, eased back on success); ticks in between decide on the last answer while it is under `jev_answer_ttl_s` (12 s), and a directional trade fires only on a fresh answer. The gateway request prefers `typesafe-ai` via `providerOptions`. Stale data means the age of our fetch at decision time (`max_stale_data_age_s`, 5 s); the venue book's last-change age is reported as `book_age_s` and never vetoed. A paper session whose gateway refuses billing fails immediately instead of running on the mock. `alpaca_paper_client.py` is paper-only by construction (no live URL, no base-URL parameter); all Alpaca calls share one ~180/min limiter per key. Modes: `shadow` (default; real data, never orders; forced for any mock decider) and `paper` (admin-only, needs a real Jev key). Session risk limits may only be lowered (`validate_limit_overrides`). Keys: `alpaca_paper` is stored as encrypted JSON `{"key_id","secret"}`; non-`PK` (live) key IDs are rejected.

**Portfolio performance (`services/price_history_service.py`, `services/performance_calc.py`, `routers/portfolio_performance.py`):** `price_bars(symbol, date, close, fetched_at)` stores 5 years of yfinance *adjusted* daily closes per symbol. A refresh always replaces a symbol's whole window (adjusted closes are revised after every dividend/split, so stitching fetches would create fake jumps). Rows are fresh for 12 h; downloads run two at a time with retry back-off, and a symbol that still fails is not retried for 5 min (Yahoo rate-limits bursts with `YFRateLimitError`). A nightly job (`price_history_refresh`, weekdays 22:30 UTC) force-refreshes every ticker in each portfolio's latest snapshot plus SPY/QQQ. `performance_calc.py` is pure: holdings-based TWR, where each day's return uses the holdings at the previous close, so a new snapshot is a cash flow, not a gain. The benchmark's calendar is the master calendar (crypto weekend moves fold into Monday), the forward fill is capped at 7 days, and each symbol gets one constant FX factor (today's rate), so returns are local-currency returns. Modes: `actual` follows the snapshot timeline (each upload applies from its UTC upload date; the last upload of a day wins); `current` is a what-if holding today's shares over the whole range; `auto` picks `actual` once there are ≥ 30 days of upload history. Unpriced holdings and a missing benchmark are reported in `warnings`, never silently zeroed. Frontend: **Performance** tab (`components/portfolio/PerformancePanel.tsx`, figures in `lib/performanceChart.ts`, types/helpers in `lib/performance.ts`).

**Portfolio risk (`services/risk_calc.py`, `routers/portfolio_risk.py`):** Describes the portfolio *as held today*: current value weights (latest snapshot × latest stored close × FX factor) applied to each holding's daily returns over the lookback, on the benchmark's calendar. Holdings with real prices on fewer than 80% of the lookback's trading days (or fewer than 20), or no price, are left out (days before a listing would otherwise count as flat) and named in `warnings` (with the share of value covered). `risk_calc.py` is pure (numpy): annualised volatility, beta/correlation vs the benchmark, 1-day historical VaR/CVaR at 95% (also in money), max drawdown of today's weights, concentration (HHI, effective holdings, top-1/top-5 weight), each holding's share of portfolio variance (`w_i·(Σw)_i / wᵀΣw`), a correlation matrix (largest 20 holdings), clusters of holdings with pairwise correlation ≥ 0.8 (union-find), and a 1-year block-bootstrap Monte Carlo (2,000 paths, 5-day blocks, fixed seed so numbers don't jump between loads). Stress scenarios (`STRESS_SCENARIOS`: GFC, COVID, 2022 rates, Aug 2024 carry unwind, 2025 tariffs) replay each holding's real move when the 5-year store covers the window; otherwise they use beta-vs-SPY × the S&P 500 move (stored SPY prices, or the hard-coded index-level move for windows older than the store), floored at −100% per holding. Every row says how it was built. Frontend: **Risk** tab (`components/portfolio/PortfolioRiskPanel.tsx`, figures in `lib/riskChart.ts`, types/helpers in `lib/risk.ts`). Shared helpers for both price-history endpoints live in `services/portfolio_pricing.py`.

**Rebalancing (`models/portfolio_target.py`, `services/rebalance_calc.py`, `routers/portfolio_rebalance.py`):** `portfolio_targets(portfolio_id, ticker, weight, band)` holds per-ticker target weights (fractions, summing to 1 ± 0.001, enforced on PUT, which replaces the whole set) and absolute tolerance bands (default ±5pp). A held ticker without a target counts as 0% (a rebalance sells it, with a warning). A target that isn't held yet is a buy. Prices are the latest stored close × today's FX factor; unpriced targets are dropped and the rest re-normalised. `rebalance_calc.py` is pure, with four modes:
- `full`: every position to target, plus optional new cash.
- `bands`: only positions outside their band go back to target; in-band positions fund the shortfall or absorb the surplus in proportion to their distance from target.
- `contribute`: buy-only, split in proportion to each underweight's shortfall; once every shortfall is filled, the excess follows the targets.
- `withdraw`: sell-only, mirroring contribute.

`whole_shares` rounds stocks (not crypto) with buys down and sells up, so the plan always stays funded. Trades under max($1, 0.05% of value) are dropped. A cash leftover within a cent per trade is reported as 0 (cent-rounding noise). Sells are listed first. The output is a plan only; AgentFloor never trades. Frontend: **Rebalance** tab (`components/portfolio/RebalancePanel.tsx`, helpers in `lib/rebalance.ts`):
- a drift chart (current weight vs target ± band);
- a targets editor with "Current weights" / "Equal weight" presets, a sum check and "Scale to 100%";
- mode pills;
- a trades table that flags sells which also carry a trim signal (from the Holdings tab's trim-signals query);
- CSV download.

**Transaction ledger (`models/portfolio_transaction.py`, `services/ledger_calc.py`, `services/ledger_service.py`, `routers/portfolio_ledger.py`):** `portfolio_transactions` rows (`trade_date`, `type` BUY/SELL/SPLIT/DIVIDEND/INTEREST/FEE/DEPOSIT/WITHDRAWAL, `symbol`, `quantity`, `price`, `amount`, `fees`, `account`, `currency`, `source` manual/csv/opening, and `seq` to order same-day rows).
- **Opting in:** a portfolio becomes **ledger-backed** (`portfolios.holdings_source = "ledger"`) once it has transactions. `ledger_service.sync_holdings` then re-derives the holdings after every change into one reused snapshot (`broker="ledger"`), so every existing feature keeps reading snapshots unchanged. On a portfolio that already has holdings, the first add or real import returns 409 (`ensure_holdings_not_replaced`) unless it sends `replace_holdings`, which the UI only does after a confirmation; otherwise those holdings would vanish from the derived snapshot.
- **Lock:** while ledger-backed, `ensure_not_ledger_backed` makes CSV holdings uploads and inline holding add/edit/delete return 409. The Holdings tab turns read-only with a banner, and its Import button opens Transactions. Deleting every transaction (`DELETE /ledger`) returns the portfolio to snapshot-backed with the last derived holdings (an empty derived snapshot is dropped instead). Deleting the last transaction individually is an undo: it always drops the derived snapshot, which brings back the holdings from before the ledger.
- **Maths:** `ledger_calc.py` is pure. It replays transactions into lots per (account, symbol) with FIFO/HIFO/average cost (`portfolios.cost_basis_method`; average pools the basis but takes quantities FIFO so holding periods stay meaningful). A SELL can also name the lots it closes (`portfolio_transactions.lots`: `[{buy_id, quantity}]`, `Tx.picks`), as brokers such as UBS allow: those lots go first, the rest follow the method, and a chosen lot that isn't open falls back with a warning. The API checks each chosen lot is a BUY of the same symbol and account; `GET /portfolio/{id}/lots?symbol=&on=&account=&exclude=` lists the lots open on a date for the picker (`components/portfolio/LotPicker.tsx`, in the add form and per sale in the Transactions table). Buy fees go into the cost basis and sale fees reduce proceeds. Splits scale lots. A sale beyond what is held only realises the held quantity and warns (no shorts). Realised gains are short or long term (held more than 365 days). It also tracks income (dividends, interest), fees, cash and net contributions per account (cash is only meaningful once deposits are recorded: `cash_tracked`). Totals are grouped by currency, not converted.
- **Getting data in:** bootstrap creates one opening BUY per current holding at its average cost. CSV import runs in the browser (`lib/ledger.ts`: parse, guess columns from broker headers, normalise broker wording such as "YOU BOUGHT" or "Qualified Dividend", take absolute values, and derive a missing price from amount ÷ quantity). The server validates every row (dry run), then inserts all of them or none.
- **Performance:** for a ledger-backed portfolio, the actual-holdings timeline comes from `holdings_timeline` (real trade dates). The report adds `mwr_period` / `mwr_annualised`, an IRR via `performance_calc.xirr` (bisection), where the opening value, buys and sales at trade price ± fees, and the ending value are the flows. Dividends are already in the adjusted prices, so they are not counted again.
- **Frontend:** **Transactions** tab (`components/portfolio/TransactionsPanel.tsx`, `ImportTransactions.tsx`):
  - an empty state with start from holdings, import CSV and add;
  - summary tiles (realised gains this year and all time with the short/long split, dividends and interest, fees and cash);
  - cost-basis pills;
  - an add form whose fields follow the type;
  - the transactions table;
  - open lots per position;
  - realised gains by year and term;
  - "Stop using the ledger".

**Dividend income (`models/dividend.py`, `services/dividend_service.py`, `services/income_calc.py`, `routers/portfolio_income.py`):**
- **Store:** `dividend_history(symbol, ex_date, amount)` holds 10 years of per-share cash dividends from yfinance (`Ticker.dividends`, split-adjusted, by ex-date). `dividend_sync(symbol, fetched_at, payments)` marks each symbol as fetched, so non-payers aren't refetched on every request. Like the price store, a refresh replaces a symbol's whole history. Rows are fresh for 24 h; downloads run two at a time with retry back-off, and a failing symbol cools down for 5 min. A nightly job (`dividend_refresh`, weekdays 23:05 UTC) force-refreshes every held ticker.
- **Maths:** `income_calc.py` is pure.
  - Frequency comes from the median gap between the last 9 payments.
  - The forward dividend is the median of the last year's payments × payments per year, so a special dividend can't inflate it.
  - Next ex-dates step forward from the last one by that gap.
  - A symbol whose last payment is older than max(400 days, 1.5 gaps) is suspended and counts as paying nothing.
  - 5-year growth compares the last year's payments with the same *number* of payments ending about five years earlier, annualised. Calendar windows would let payment timing put 3 payments in one year and 5 in the other.
  - The projection grows income at the income-weighted 5-year growth, capped to −10%…15%, with prices growing at the same rate (constant yield). With reinvestment it compounds by (1 + yield) a year as well.
- **Report:** amounts use today's shares (latest snapshot), the latest stored close and today's FX factor. `received` is actual cash from the ledger's DIVIDEND transactions when the portfolio is ledger-backed, otherwise an estimate from today's shares × each past ex-date's dividend (24 months, labelled by `source`). `portfolios.income_target_monthly` is a per-portfolio dollar goal; the investor profile's categorical `income_goal` is returned for UI hints.
- **Frontend:** **Income** tab (`components/portfolio/IncomePanel.tsx`, helpers in `lib/income.ts`, projection figure in `lib/incomeChart.ts`): headline, stat tiles, a goal card with progress bar and editor, a 12-month calendar by ex-month (hover/tap lists the payers), a per-holding table, income received over 24 months, and the 10-year with/without-reinvestment projection with its assumptions spelled out. Ledger changes invalidate the income query.

**Tax tools (`services/tax_calc.py`, `routers/portfolio_tax.py`):** informational only, simplified US rules, and every response carries a `disclaimer`. Needs a ledger-backed portfolio; otherwise it answers `available: false`.
- **Lots:** `ledger_calc` lots now remember the BUY that opened them (`Lot.tx_id`), and realised rows record `open_tx_id` / `sell_tx_id`.
- **Wash sales:** `wash_sales` matches each loss row against BUYs of the same symbol within ±30 days in *every* portfolio the user owns, earliest first. Each replacement share absorbs one loss share, and shares sold in the same sale never count as their own replacement. The disallowed loss is reported (code `W`, `adjustment`, `adjusted_gain`) but not pushed into the replacement lots' basis.
- **Report:** `tax_year_report` returns Form 8949-style rows (one per lot sold) plus totals per currency and term (short/long, from the ledger's 365-day rule).
- **Harvest:** `harvest_candidates` lists open lots whose unrealised loss in the display currency (latest close × FX factor) is at least `min_loss`, largest first. Each carries its term, days to long term, any BUY of the symbol in the last 30 days (selling now would be a wash sale) and the "don't rebuy before" date.
- **Replacements:** `replacement_ideas` ranks a fixed pool of liquid ETFs (`REPLACEMENT_POOL`) by daily-return correlation over the last year (≥ 0.3, labelled close / moderate / loose at 0.8 / 0.6). It skips funds that track the same index as the holding (`SAME_INDEX`). It is fetched on demand because the first call loads about 20 symbols into the price store.
- **Frontend:** **Tax** tab in the portfolio's overflow menu (`components/portfolio/TaxPanel.tsx`, helpers in `lib/tax.ts`):
  - a not-tax-advice banner;
  - year pills, totals tiles and the 8949-style table with wash-sale notes and a CSV download;
  - loss-harvest candidates with minimum-loss pills, wash-sale warnings and "Similar funds";
  - an empty state that links to Transactions.

  Ledger changes invalidate it.

**Net worth (`models/net_worth.py`, `services/net_worth_calc.py`, `services/wallet_service.py`, `routers/net_worth.py`):**
- **Items:** `net_worth_items` holds what a user owns or owes outside their portfolios. Each has a `kind` (asset/liability), a category (`ASSET_CATEGORIES` / `LIABILITY_CATEGORIES`), a name, a currency and notes. Values live in `net_worth_valuations(item_id, date, value)`: each update records a value on a date, and the latest value on or before a day is the item's value that day. An item counts from its first value; at least one value must remain. Limit: 200 items per user.
- **Crypto wallets:** a wallet item has `wallet_chain` btc|eth and a public address. Its valuations hold coin balances, priced at report time from the price store (`BTC-USD`/`ETH-USD`) × the USD → display rate.
  - Balances are read-only, with no keys: BTC from mempool.space, native ETH from a public JSON-RPC node.
  - Sync happens on create, on demand, and nightly (`wallet_sync`, 23:20 UTC).
  - A failed sync keeps the last balance and stores `sync_error`.
- **Report:** portfolios use their Performance series (mode `auto`) and count from where it starts. `net_worth_calc` (pure) forward-fills everything onto the portfolios' trading days, or weekly points for 3Y/5Y. It returns assets, liabilities, net worth, the debt ratio, and the split by category (portfolios grouped as "Portfolios"). It also flags manual values older than 180 days. All conversions use today's FX rate.
- **Frontend:** the `/net-worth` page (`components/networth/NetWorthView.tsx`, helpers in `lib/netWorth.ts`, figure in `lib/netWorthChart.ts`) has:
  - a headline with the change over the range, range pills and tiles;
  - a net-worth/liabilities chart with a note naming items that start inside the range;
  - category bars;
  - an add form (asset, liability or wallet);
  - per-item Update value (any past date), History (delete a value), Sync and Remove;
  - the portfolio list.

**Backtest Lab (`models/backtest.py`, `services/backtest_calc.py`, `services/backtest_runner.py`, `routers/backtests.py`):** wraps `tradingagents.backtest.Backtester`. The agents re-run on a grid of past dates, and each call is scored on the next `horizon_days` bars against buy-and-hold, always-hold, SMA-crossover and random baselines, with the same costs.
- **Running:** `backtest_runner` runs one backtest at a time per server (others wait as `pending`). The harness runs in `asyncio.to_thread`, and each finished decision arrives through `on_trade`: it is saved every 3 s, and an abort request takes effect there, after the decision in flight.
  - Every backtest gets its own temporary TradingAgents `results_dir`, so walk-forward reflection (agent memory) stays inside it and never reaches live runs. The directory is deleted afterwards.
  - Real runs patch the provider environment through `trading_agent_runner.provider_env` under the same lock as live runs, and stop at `budget_usd` (status `stopped`).
  - On boot, pending/running rows become `interrupted` with a report over what finished.
- **Dry runs:** `dry_run` uses the harness's stub model (always BUY) to check dates, prices and scoring for free.
- **Limits:** 5 tickers; 120 decisions (300 for a dry run); dates must end a horizon before today; a real run needs a budget (≤ $200) and a stored key for keyed providers; 3 queued/running backtests per user.
- **Contamination:** `MODEL_CUTOFFS` holds approximate training cutoffs. `cutoff_for` matches the longest name prefix only when what follows is a date, a word suffix or an Ollama tag, never another version number, so "gpt-5.5" does not inherit gpt-5's cutoff. Users can override the cutoff.
  - `build_report` labels each decision out-of-sample (after the cutoff), in-sample or unknown. The headline uses out-of-sample decisions only: there is none when every date is in-sample, and all decisions with a warning when the cutoff is unknown.
- **Metrics:** each decision date is an equal-weight period: total return, max drawdown, Sharpe annualised by decisions per year, hit rate and expectancy over BUY/SELL calls, the same curves for each baseline, and excess vs buy-and-hold.
- **Model leaderboard:** `backtest_calc.leaderboard` groups live runs' outcomes by provider · model, depth or analyst set. It reports 7- and 30-day accuracy (HOLD not scored), direction-signed return, and excess return vs SPY over the same window (stored SPY closes).
- **Frontend:**
  - `/runs/backtest` (form with a dry/real switch, decision count, model picker, analysts, budget, a cutoff override and a sentence on how the dates sit against the cutoff; plus the list);
  - `/runs/backtest/[id]` (progress, Stop/Delete, the cutoff note, headline tiles, an in-sample vs out-of-sample comparison, a growth-of-1 chart with the cutoff marked, the baselines table and each decision);
  - a "Which setup calls it best?" leaderboard on `/runs/performance`.

  Components are in `components/backtest/`, helpers in `lib/backtest.ts`.

**Learning loop (`services/learning_service.py`, `models/run_reflection.py`, `routers/learning.py`):** opt-in per user (`users.learning_enabled`, `learning_horizon_days` 7 or 30).
- **Memories:** each user has their own TradingAgents results directory, `$TRADINGAGENTS_RESULTS_DIR/users/<id>` (default `./results`), which holds the agents' BM25 memories. `execute_run` points a live run at its owner's directory only while learning is on (`live_results_dir`), so lessons never cross users.
- **Reflection:** a completed run is due once the horizon has passed.
  - The outcome comes from the keyless price store (`outcome`, pure): the close on or before the analysis date vs on or before date + horizon. BUY scores the move, SELL its inverse, HOLD zero, and the move itself is passed as context.
  - The agent state is rebuilt from `Report.raw_report` (minus messages). `reflect_and_remember` runs with the run's own provider, model and depth, five LLM calls on the user's key, under the same env lock as live runs.
  - `run_reflections` keeps one row per run (done / failed / skipped). Failed attempts are retried on later passes up to `MAX_ATTEMPTS` (3). Each pass handles at most 10 runs per user.
- **Schedule:** the nightly job `learning_reflections` runs at 01:10 UTC; "Reflect now" runs a pass for one user.
- **Hindsight on live runs:** `RunResponse` carries `training_cutoff` and `hindsight_risk` (analysis date on or before the model's cutoff, via `backtest_calc.cutoff_for`). The run page shows a banner, and the model leaderboard leaves those runs out (`excluded_in_sample`).
- **Frontend:** Settings → **Learning loop** (`components/settings/LearningSection.tsx`, helpers in `lib/learning.ts`): an on/off toggle, horizon, memory counts per agent, reflection counts, Reflect now, Clear memories, and recent reflections with the move, the score and any error.

**MCP server (`app/mcp_server.py`, `models/mcp_token.py`, `routers/mcp_tokens.py`):** AgentFloor is exposed to MCP clients (Claude Code/Desktop, Cursor, …) at `/mcp` (behind nginx `https://<host>/api/mcp`).
- **Transport:** FastMCP from the `mcp` SDK in stateless Streamable HTTP mode with JSON responses (no SSE, so nginx needs no change). `mcp` arrives transitively via `chainlit` in `uv.lock`: it could not be declared directly because `uv lock` currently fails for the Python 3.14/Windows split (tradingagents 0.7 is unavailable there). The app still boots without it, and then `/mcp` answers 503.
- **Routing:** `McpDispatch` (ASGI middleware added in `main.py`) hands exactly `/mcp` and `/mcp/` to the MCP app and everything else to FastAPI. A `Mount("/mcp")` would only match `/mcp/...`. The session manager runs inside the FastAPI lifespan.
- **Auth:** `PatVerifier` (FastMCP `TokenVerifier`) resolves `Authorization: Bearer af_...` to the user via the SHA-256 lookup. It rejects revoked or expired tokens and records `last_used_at` at most every 5 min. Tools read the caller from `get_access_token()`, and every query is scoped to that user.
- **Scopes and tools:**
  - `read`: `list_portfolios`, `get_holdings`, `get_performance`, `get_risk`, `get_rebalance_plan`, `get_regime`, `list_runs`, `get_run_report`, `get_latest_insight`, `list_alerts`, `get_income`, `get_tax_report`, `get_net_worth`, `get_filings`, `get_xray`.
  - `research` (opt-in when creating the token) adds `start_analysis` (creates a Run labelled "via MCP" with the user's default LLM, through the shared `services/run_launcher.launch_run`) and `generate_portfolio_insight`.
  - No tool places orders and JEV Lab is not exposed.
- **DNS-rebinding:** host checking is disabled on purpose. Every request needs a bearer token that a rebinding page cannot attach, and the check would reject proxied hosts.
- **Tests:** `tests/test_mcp_server.py` drives a fresh `build_server()` with the official MCP client over an in-process ASGI transport. The ASGI transport doesn't run the lifespan, so each test runs its own session manager.
- **Frontend:** the Settings **MCP access** section (`components/settings/McpAccessSection.tsx`, helpers in `lib/mcp.ts`) creates a token (name, expiry, research opt-in), shows it once with copy-ready config for Claude Code, Cursor and Claude Desktop (via `mcp-remote`), and lists and revokes tokens.

**Alerts (`models/alert.py`, `services/alert_rules.py`, `services/alert_engine.py`, `routers/alerts.py`):** Per-user `AlertRule` rows (`kind`, `params` JSONB, `channels`, `cooldown_hours`, `enabled`, engine `state`) and `AlertEvent` rows (the in-app inbox, with a `delivery` outcome per channel). Kinds in `alert_rules.KINDS`:
- **Level rules** fire when the condition *becomes* true and re-arm once it is false. The first check counts as a transition, so a rule created while already true fires once. Kinds: `price_above`, `price_below`, `daily_move` (re-arms each trading session, keyed by the quote's previous close, not the UTC date), `ma_cross` (50/200-day, on stored daily closes), `portfolio_drawdown` (Performance report), and `position_weight` (fires per newly oversized holding).
- **Change rules** record a baseline on the first check, then fire on change: `regime_change` (Markov, optionally into a given regime) and `verdict_change` (a newer completed run with a different verdict).

`alert_rules.evaluate` is pure. The engine's `MarketData` fetches observations with a per-pass cache, so N rules on one ticker cost one fetch, and tests subclass it. The scheduler job `alert_evaluation` (every 15 min) runs `evaluate_all_alerts`: evaluate, persist state, then deliver. A firing inside the cooldown is swallowed and consumes the transition. A pass that is still running makes the next one skip (in-process lock, single worker), so overlapping passes can't double-fire. Inbox items are marked read only by an explicit action (Mark read, or opening their link). Channels: `inbox` (always), `email` (the user's address; SMTP stub when unconfigured), `webhook` (the rule's portfolio's `PortfolioDeliverySettings`, json/slack/telegram). Webhook needs `portfolio_id`; ticker rules may set one for that. "Check now" (`check_rule`) is a dry run: no state change, nothing fires. 100 rules per user. Frontend: `/alerts` page (`components/alerts/`), an unread badge on the **Alerts** nav item (polled every 60 s) and a dot on the mobile menu button, plus alert shortcuts in `TickerDrawer` (`/alerts?ticker=X&kind=Y` prefills the form).

**Natural-language watch rules (`services/alert_compound.py`, `services/alert_compiler.py`, `services/run_launcher.py`, `components/alerts/DescribeAlert.tsx`):** roadmap 3.2. The LLM only *proposes* a rule; evaluation stays deterministic.
- **Compound rules:** kind `compound` with params `{op: and|or, scope: ticker|holdings, sectors: [...], conditions: [...]}` (1–5 conditions). Conditions: `price_above`/`price_below` (ticker scope only), `daily_move` (with `direction` any/up/down), `ma` (close vs 50/200-day), `regime` (current Markov regime), `verdict` (latest completed run), `weight_above` (share of the rule's portfolio). Scope `holdings` reads the portfolio's latest snapshot; `sectors` keeps holdings whose `ticker_metadata` sector *or* industry contains (or is contained in) a filter, ignoring case and punctuation ("semiconductor" matches "Semiconductors", "Health Care" matches "Healthcare"); unknown sectors never match a filter. At most 60 holdings per pass. `alert_rules.rule_scope` decides whether a rule needs a ticker or a portfolio; a `weight_above` condition also needs one.
- **Evaluation:** `alert_compound.evaluate` (pure) applies Kleene AND/OR per ticker (`None` when data is missing) and level semantics *per ticker*: a ticker fires when it starts matching and re-arms once it doesn't; an unknown result neither fires nor re-arms; tickers that leave the scope are forgotten; a rule with a `daily_move` condition re-arms each ticker when its previous close changes. One event per pass lists every newly matching ticker (`data.matched`). `alert_engine.observe_compound` fetches readings cheapest first (weight, verdict, quote, MAs, regime), stops for a ticker once its outcome is decided, and fetches quotes and regimes concurrently across tickers.
- **Re-run action:** the `alert_rules.rerun_analysis` column (any kind but `portfolio_drawdown`). On firing, `alert_engine.rerun_analyses` starts a Run labelled "via alert" with the user's default LLM for each ticker the event is about (`rule_tickers`: the rule's ticker, a compound's matches, or position_weight's new holdings), at most `MAX_RERUNS_PER_EVENT` (3). A run for the same ticker created in the last 20 h (pending/running/completed) is linked instead of starting another. Outcomes go to `event.delivery["analysis"]` and `event.data.analyses`; `GET /alerts/events` adds each analysis's current status and verdict. Research only: never an order.
- **Compiler:** `POST /alerts/compile {text}` (3–500 chars) picks the user's LLM (`llm_selection.pick_llm_for_user`), sends one prompt describing the rule format plus the user's portfolio names (`alert_compiler.build_prompt`), and parses the JSON reply (`parse_reply`, `tidy_params` forgives numbers as strings and case). The proposal goes through `_normalize`, the same validation as `POST /alerts/rules`. Portfolio names resolve case-insensitively; a rule that needs a portfolio gets the user's only one, or `needs_portfolio: true` when there are several. Webhook delivery without a portfolio is dropped and listed in `unsupported`. Responses are 200 with `ok`, `rule` (ready to POST), `unsupported` (parts it left out), `problems` (why it isn't a valid rule) and `llm`; no LLM key is 422, a provider failure 502. Nothing is ever saved. Test seam: `alert_compiler.ask_llm`.
- **Frontend:** the **Describe an alert** card on `/alerts` (`DescribeAlert.tsx`): a text box with examples, then "Here's what I'll watch for" (the deterministic `describeRule` sentence and firing note from `lib/alerts.ts`, not the model's words), all/any toggle and removable conditions for compound rules, what was left out, portfolio (required when needed), cooldown, channels, the re-run checkbox, then Save or Discard. The manual form ("Or build one yourself") has the re-run checkbox too; rules show "re-runs the analysis"; inbox events link each analysis with its verdict.

**ETF look-through (`models/fund_profile.py`, `services/lookthrough_calc.py`, `services/fund_lookthrough_service.py`, `routers/portfolio_xray.py`, roadmap 3.4):**
- **Store:** `fund_profiles` holds one row per held ticker (`kind` fund/stock/unknown), shared across users. A row is fresh for 7 days; a failed lookup keeps the last good data, sets `error` and retries after a day. Refresh runs on first visit, on POST, and weekly (`fund_profiles_refresh`, Sundays 22:30 UTC).
- **Sources:** SEC N-PORT gives full holdings when `edgar_service.contact_configured()`; a trust files one per fund, so `_latest_nport` checks each filing's opening bytes (`edgar_service._http_get_prefix`) for the series before downloading it, and ignores filings older than 270 days. Unit and commodity trusts (SPY, GLD) don't file N-PORT. Yahoo gives the top 10, sector split and whether a ticker is a fund at all (`_yahoo_profile`, the test seam); only Yahoo decides that, because the SEC fund list shares tickers with stocks on other exchanges, so a ticker Yahoo can't find stays `unknown` unless it was a fund before. Crypto never reaches Yahoo.
- **Maths (`lookthrough_calc`, pure):** holdings are keyed by SEC CIK when known, so share classes and direct holdings meet, then by ticker, then by name. Names match on `name_key`, which ignores punctuation, spacing, corporate suffixes and the state the SEC appends after a slash; companies that changed their legal name (ExxonMobil, Zoom) match only by ticker. Unknown fund weight is reported as `uncovered_weight` and never spread over known names, so company exposures are minimums. Overlap is the sum of the smaller weights over shared names.
- **Output:** `build_report` reads stored data only. `prompt_block` feeds the AI brief through `portfolio_insight_runner._xray_block`; MCP `get_xray` returns the report.

**SEC filing digests (`models/sec_filing.py`, `services/filing_calc.py`, `services/edgar_service.py`, `services/filing_digest_service.py`, `routers/filings.py`):** roadmap 3.3, "what changed" in holdings' SEC filings.
- **EDGAR client:** free and keyless, but every request sends `settings.sec_user_agent` (`SEC_USER_AGENT`; EDGAR answers 403 without a contact email, so with none set `contact_configured()` keeps the tab, refresh and nightly job from calling it and the report sets `needs_contact`) and goes through one limiter at about 6 requests a second, with retry back-off on 429/5xx. `edgar_service._http_get` is the test seam. Parsing uses only the standard library (`html.parser`, `xml.etree`).
- **Store (shared across users):** `sec_ciks` (ticker → CIK from `company_tickers.json`, refreshed weekly; tickers normalised `BRK.B` → `BRK-B`), `sec_filings` (10-K, 10-Q and 8-K from the last 120 days, plus the previous 10-K/10-Q each one is compared with as `digest_status="reference"`, and Form 4s from the last 90 days, at most 25 per ticker), `sec_filing_texts` (extracted Risk Factors paragraphs or 8-K text, so a filing is downloaded once), `sec_insider_trades` (non-derivative Form 4 rows; Form 4s the company filed as an owner of *another* issuer are skipped), `sec_sync` (per-ticker fetch time, fresh for 6 h, and the last error). Funds, crypto and foreign listings have no CIK and are reported as `no_filer`.
- **Maths (`filing_calc`, pure):** `html_to_paragraphs` (skips hidden inline-XBRL headers, scripts and styles); `extract_section` takes the *longest* span from an "Item 1A. Risk Factors" heading to the next item heading, so the table of contents never wins; `diff_paragraphs` matches each new paragraph to its most similar old one by Jaccard on 4-word shingles with digits folded (a new fiscal year isn't a change), through an inverted index: ≥ 0.85 unchanged, 0.35–0.85 reworded, below that new, and old paragraphs nothing resembles are removed; `ranked` puts whole new/removed paragraphs before rewordings. Also `parse_form4` (roles, 10b5-1 plans from `aff10b5One` or a footnote, trades), `summarize_insiders` (open-market P/S only; grants, exercises, tax withholding and gifts are counted as other), 8-K `item_labels` with `NOTABLE_ITEMS` (e.g. 4.02 non-reliance, 5.02 officer changes), `trim_8k` (drops the cover page and signature block), `deterministic_summary`, the digest prompt, and `prompt_block` for the AI brief.
- **Digests:** `prepare` diffs 10-K/10-Q risk factors against the previous filing of the same form, or keeps an 8-K's text plus up to two exhibits (usually the press release), and stores a deterministic `summary` either way. `digest` makes one LLM call per filing with the team's first configured key (`pick_llm_for_user(db, None)`), never per user. **Every point must quote its excerpt verbatim** (`validate_digest`, ignoring case, quotes and spacing); points that don't are dropped, duplicates too, and a reply with no cited point is stored as `uncited` and never shown. Statuses: `pending` → `prepared` → `done` / `uncited` / `failed` (retried up to 3 times); `not_applicable` when there is nothing to diff. Without a key, filings stay `prepared` with their plain summary and are digested once a key exists. Test seam: `filing_digest_service.ask_llm`.
- **Refresh:** nightly job `sec_filings_refresh` (weekdays 23:40 UTC) for every held ticker; `GET` starts a background refresh for its portfolio when the store is missing or older than 24 h; `POST …/refresh` forces one. One refresh runs at a time per server (`_sync_lock`); `running` lists portfolios being refreshed, so the UI can poll.
- **Report:** `filing_digest_service.report` (DB only) returns filings newest first with item labels, counts, the previous filing, and digest points with a `kind` (added/removed/reworded/document) and a text-fragment `link` (`#:~:text=`) that opens the filing at the quote; removed passages link to the previous filing. Insiders per ticker: buys/sells, values, net, planned sells, and the latest open-market trades.
- **AI brief:** `portfolio_insight_runner._filings_block` adds the last 30 days (cited digests and plain summaries only, plus insider totals) to the insight prompt, which is told to mention material filings and never add details. MCP: `get_filings`.
- **Frontend:** **SEC filings** tab in the portfolio overflow menu (hidden for all-crypto portfolios; `components/portfolio/FilingsPanel.tsx`, helpers in `lib/filings.ts`): 30/90/120-day and form filters, Refresh with polling while EDGAR is checked, filing cards (form, date, 8-K item chips with notable ones in amber, the digest headline and quoted points with "in the filing" links, the plain summary, links to the filing and the previous one), an insider-trades column (net, buys/sells, 10b5-1 tags, latest trades linked to the Form 4), and a no-key banner. The Holdings tab's morning brief adds a "SEC filings this week" line (`briefLine`) linking to the tab.

**Auth flow:** `POST /auth/register` — first user gets `admin` role automatically. Subsequent registrations require a valid invite token. `POST /auth/login` returns a JWT. All other routes use `get_current_user` (dependency in `app/dependencies.py`) which validates the Bearer token and loads the `User` row. `POST /auth/invite` generates a signed invite token and emails the link; when SMTP is not configured the invite URL is returned in the response body (`invite_url` field) so the admin can copy-paste it.

**Run lifecycle:**
1. `POST /runs` creates a `Run` row and immediately calls `start_run()` from `job_manager.py`.
2. `job_manager.py` wraps `execute_run()` in an `asyncio.Task` and stores it by `run_id`.
3. `trading_agent_runner.py` runs `TradingAgentsGraph.propagate()` in a thread (`asyncio.to_thread`) because TradingAgents is synchronous. A `_SyncEmitter(BaseCallbackHandler)` puts events into a `SyncQueue`; a drain coroutine transfers them to an `asyncio.Queue`; a process coroutine persists `AgentEvent` rows and broadcasts over WebSocket. `propagate()` returns `(final_state, recommendation)` — the recommendation's `.signal`/`.rationale`/`.entry_reference_price`/`.stop_loss`/`.target_price` fields are used directly to populate the `Report`.
4. `DELETE /runs/{run_id}` calls `abort_run()` which cancels the asyncio task, triggering `CancelledError` in the runner, which sets status to `aborted`.
5. `GET /runs/{run_id}/report` returns the `Report` row created at completion.
6. On completion, `outcome_service.py` lazily fetches closing prices from Finnhub (`/stock/candle`) at +7d/+14d/+30d/+90d and persists a `RunOutcome` row.

**Elliott Wave analysis (`backend/elliott_wave/`):** Self-contained package vendored into the repo. Entry point is `services/wave_service.py` which wraps the package in async helpers. Architecture: `AnalysisOrchestrator` (top-level) → `SwingDetector` (ZigZag pivots) + `ElliottEngine` (wave labelling) + `FibonacciEngine` (retracement/extension levels) + `SignalEngine` (trade region scoring) + `ChartPayloadService` (Plotly-ready JSON). Results are cached in-process for 4 hours keyed by `ticker:period:interval:profile`. Four analysis profiles: `full_confluence`, `elliott_focused`, `fib_only`, `swing_only`. The `GET /wave/{ticker}` endpoint returns a compact summary (scenario, direction, trade zone, confidence) suitable for badges; `POST /wave/{ticker}/analyze` returns the full chart payload for the `WavePanel` Plotly chart. The portfolio batch endpoint (`GET /portfolio/{id}/wave`) runs summaries concurrently for all holdings via `asyncio.gather` with a semaphore(5) cap.

**Watchlist & Scheduler:** `watchlist.py` router manages per-user watchlists (one per user, auto-created on first access). Each `WatchlistItem` stores ticker, LLM config, and an optional cron expression. `services/scheduler.py` wraps APScheduler 4.x `AsyncScheduler`. On startup it calls `start_in_background()` (required — `__aenter__` alone leaves the scheduler in `RunState.stopped`) then `_reload_jobs()` to register all enabled items. After every watchlist mutation the router calls `reload_jobs()` so changes take effect without restart. Additionally, a system-level job (`daily_portfolio_insights`, weekdays hourly at :15 UTC) calls `_fire_daily_portfolio_insights()`, which picks the first configured LLM provider key and generates a `PortfolioInsight` for every portfolio where it is 9 AM in its delivery timezone, that has holdings and no insight in the last 12 hours.

**WebSocket:** `ws_manager` (singleton in `websocket_manager.py`) maintains `dict[run_id, list[WebSocket]]`. The WS endpoint at `/ws/runs/{run_id}` loops on `receive_text()` to keep the connection alive; clients send `"ping"` every 30 s.

**Encryption:** API keys are stored encrypted. `services/encryption.py` derives a `Fernet` key from the 64-hex-char `ENCRYPTION_KEY` setting.

**Config:** All settings are in `app/config.py` via pydantic-settings. Env var names: `DATABASE_URL`, `JWT_SECRET`, `ENCRYPTION_KEY`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `FRONTEND_URL`, `SEC_USER_AGENT` (name and contact email EDGAR asks for). `SEC_USER_AGENT` identifies the app to SEC EDGAR. Local model servers (Ollama, vLLM, LiteLLM) are not env vars: their base URL is stored like a key in Settings → API Keys and passed to the runner (`trading_agent_runner` sets `OLLAMA_HOST` from it per run). The learning loop reads `TRADINGAGENTS_RESULTS_DIR` (default `./results`).

**TradingAgents version:** `tradingagents` 0.7.0 (Mai0313 fork), pinned in `[tool.uv.sources]` to its wheel URL on `files.pythonhosted.org` because the PyPI index no longer lists any releases. The `backend/patches/` install-time monkey-patch pipeline was removed when upgrading from 0.3.2; the technical analyst is now folded into the upstream `market` analyst. Legacy `"technical"` analyst selections are silently normalised to `"market"` by `app/utils/tradingagents_analysts.py`. `propagate()` now returns `(state, recommendation)` — a structured `TradeRecommendation` object with `.signal` (BUY/SELL/HOLD), `.rationale`, `.entry_reference_price`, `.stop_loss`, `.target_price` — replacing the free-text signal string. `_parse_verdict` and `_extract_trader_decision` in `trading_agent_runner.py` consume these structured fields directly.

**TradingAgents runtime patches (`services/tradingagents_grounding.py`):** Two runtime patches applied at the start of each `execute_run` call (idempotent, module-level flags). Neither modifies site-packages. (1) `apply_analyst_specific_grounding_patch()` — tightens the grounding check so an analyst section is only marked as evidence-based when the ToolMessage belongs to *that analyst's* tool set, preventing cross-analyst contamination. (2) `apply_reasoning_effort_patch()` — patches `tradingagents.llm._apply_reasoning` to skip the `reasoning_effort` kwarg when `OPENAI_BASE_URL` points to a non-native OpenAI endpoint (Groq, IONOS); both providers use an OpenAI-compatible API but reject this parameter with HTTP 400.

**Tests:** All tests share one event loop (`asyncio_default_test_loop_scope = "session"` in pyproject.toml). The `clean_db` session-scoped autouse fixture in `conftest.py` TRUNCATEs all tables before each test session: `users, runs, agent_events, reports, api_keys, run_outcomes, watchlists, watchlist_items, portfolios, portfolio_snapshots, portfolio_holdings, …, jev_sessions, jev_ticks, price_bars, alert_rules, alert_events, portfolio_targets, mcp_tokens, portfolio_transactions, dividend_history, dividend_sync, net_worth_items, net_worth_valuations, backtests, run_reflections, sec_ciks, sec_filings, sec_filing_texts, sec_insider_trades, sec_sync` (see `conftest.py` for the full list).

### Frontend (`frontend/`)

**Theming:** `next-themes` with a `ThemeToggle` button in the top nav. **Portfolio data model:** `Portfolio` → `PortfolioSnapshot` → `PortfolioHolding` (cascade delete). Each upload creates a new snapshot. Holding-level endpoints (`POST/PATCH/DELETE /portfolio/{id}/holdings/{holding_id}`) mutate the latest snapshot and keep `row_count` in sync. Prices are fetched concurrently via `asyncio.gather` and cached in-process for 1 hour.

**Portfolio Insights:** `Portfolio` also has a one-to-many `insights` relationship to `PortfolioInsight` (cascade delete). Each `PortfolioInsight` row has `status` (`pending`→`running`→`completed`/`failed`), `trigger` (`manual`/`scheduled`), LLM provider/model, and JSONB output fields: `health_score` (1–10 int), `overall_stance` (`bullish`/`bearish`/`neutral`/`mixed`), `summary`, `action_items`, `risk_alerts`, `sector_analysis`, `strengths`, `weaknesses`, and `holdings_snapshot` (prices/P&L captured at generation time). The `portfolio_insight_runner.py` service: fetches live prices (reuses Finnhub cache), fetches sector data from Finnhub `/stock/profile2` (24 h in-process cache), collects last run verdicts from the DB, builds a structured JSON prompt, calls the provider API directly via httpx (OpenAI → `api.openai.com`; Anthropic → `api.anthropic.com`; Google → `generativelanguage.googleapis.com`; Ollama/vLLM → local base URL), and parses/persists the result. Before the LLM call it computes the 1-year Performance and Risk reports in their own DB session (`_measured_metrics` → `services/insight_metrics.py`) and adds a "MEASURED PERFORMANCE & RISK" block that the model is told to quote and never contradict (returns vs benchmark, contributors, volatility, beta, VaR, risk outliers, correlated clusters, worst stress replay). The same summary is stored in `holdings_snapshot.measured`; if it can't be computed the brief is generated without it. The route and runner share `services/portfolio_performance_service.py` / `portfolio_risk_service.py`, and the routers are thin wrappers that do validation and ownership checks. Concurrency guard: only one insight per portfolio can be `pending` or `running` at a time (returns 409 if attempted). Endpoints: `POST /portfolio/{id}/insights/generate` (202), `GET /portfolio/{id}/insights/latest`, `GET /portfolio/{id}/insights`, `GET /portfolio/{id}/insights/{insight_id}`.

**Portfolio supplementary endpoints (all on `/portfolio/{portfolio_id}/`):**
- `POST /runs/batch` — queues analysis `Run` rows for holdings whose last analysis is older than `staleness_days` (default 7) or never analyzed. Accepts `llm_provider`, `llm_model`, `depth`. Returns `{ queued: [...tickers], skipped: [...tickers], message }`.
- `GET /earnings?days_ahead=30` — fetches upcoming earnings from Finnhub `/calendar/earnings` for all holding tickers concurrently; returns events sorted by date. In-process cache: 6 hours per ticker.
- `GET /fundamentals` — fetches key metrics from Finnhub `/stock/metric?metric=all` for all holding tickers concurrently; returns `{ ticker: { pe_ratio, beta, week52_high, week52_low, dividend_yield, eps_ttm, market_cap } }`. In-process cache: 6 hours per ticker.
- `GET /news?days=7` — fetches company news from Finnhub `/company-news` for all holding tickers concurrently; merges and sorts by `datetime` descending; limited to 40 articles. In-process cache: 1 hour per ticker.

All four supplementary endpoints require a Finnhub key. They return empty results gracefully if no key is configured (rather than erroring).

### Deployment

`docker-compose.prod.yml` runs four services: `db` (postgres:16), `backend`, `frontend`, `nginx`. `docker-compose.dev.yml` builds the app locally and also includes Adminer. The backend waits for the `db` healthcheck before starting. Nginx reverse-proxies `/api/` → backend, `/ws/` → backend (with WebSocket upgrade headers), and everything else → frontend. TLS is handled by `docker-compose.traefik.yml`; the bare prod stack listens on HTTP port 80.
